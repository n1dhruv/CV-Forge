# MakeMyResume

MakeMyResume builds job-specific resumes from a user's existing, verifiable career information. Instead of asking an AI model to generate a resume from scratch, the application stores experiences, projects, education, certifications, skills, and bullet points in a structured Skill Bank. It then finds the evidence most relevant to a job description, proposes controlled rewrites, requires the user to review every proposal, and produces an editable LaTeX resume and PDF.

The repository contains a Next.js frontend, a FastAPI backend, and an ARQ worker process. PostgreSQL is the source of truth, Supabase provides authentication and private file storage, Pinecone provides dense and sparse retrieval, and user-selected AI providers are accessed through LiteLLM.

## Core concept

The system separates reusable career evidence from a particular resume.

A Skill Bank item represents an experience, project, skill, education entry, or certification. Items can contain ordered bullet points, tags, dates, an organization, and supporting text. The same evidence can therefore be evaluated against many job descriptions without maintaining separate source resumes.

For each job description, MakeMyResume:

1. Extracts required skills, preferred skills, responsibilities, ATS keywords, action verbs, and explicitly named technologies.
2. Searches the user's Skill Bank for evidence relevant to every extracted requirement.
3. Returns ranked items and bullets for the user to select.
4. Rewrites only the selected bullets while preserving the original text.
5. Flags unsupported claims, new technologies, and changed numbers or metrics.
6. Requires every proposed rewrite to be approved or reverted.
7. Groups the resolved bullets into an editable LaTeX document and compiles it into a PDF.

The original Skill Bank bullets are never overwritten by resume generation. Each resume stores its own immutable original text, proposed text, review decision, LaTeX source, and version history.

## Hybrid search and reranking

Matching uses retrieval followed by reranking. This is more useful than relying on either keyword search or vector similarity alone.

When a Skill Bank item or bullet is created or updated, a worker writes two vectors to separate Pinecone indexes inside a namespace based on the user's UUID:

- A dense vector generated by the embedding provider configured by the user. Dense search can find semantically related evidence even when the job description uses different wording.
- A sparse vector generated with Pinecone's `pinecone-sparse-english-v0` model. Sparse search preserves strong lexical signals such as framework names, programming languages, and exact technical terms.

Matching processes every parsed job requirement separately:

1. The requirement is converted to a dense query embedding.
2. Dense and sparse Pinecone searches run concurrently, each retrieving up to 25 candidates.
3. Results are merged and deduplicated by source type and UUID.
4. Candidates missing either their dense or sparse vector are excluded and reported through `pending_embeddings`.
5. PostgreSQL supplies the candidate text; Pinecone is not treated as the source of truth.
6. The merged candidates are sent to the configured OpenRouter reranker with the original requirement as the query.
7. Candidates below the minimum reranker score are removed. Accepted results receive `moderate` or `strong` confidence.
8. When both an item-level result and one of its bullets match the same requirement, only the higher-scoring result is kept.
9. Results are grouped under their Skill Bank item, ordered by relevance, and limited to four matches per item.

Dense retrieval improves recall, sparse retrieval protects exact terminology, and reranking compares the actual requirement with the retrieved text before the result reaches the user. The first two stages cheaply produce a candidate set; the reranker spends its work only on that smaller set.

Matching currently runs synchronously in `POST /api/match/{jd_id}` and returns the completed result in that response. A matching worker exists in the worker registry, but the current API route does not enqueue it.

## Application workflow

### 1. Authentication and user isolation

The frontend authenticates with Supabase Auth. The API verifies each bearer token against Supabase's JWKS endpoint, validates its issuer, audience, role, expiry, and email claim, and creates the corresponding local `users` row when needed.

All owned PostgreSQL queries include the authenticated user ID. Pinecone records are isolated with one namespace per user, and private Supabase Storage paths begin with the user's UUID.

### 2. LLM configuration

Each user supplies their own completion provider, model, and API key. They may configure a separate embedding provider, model, and key or reuse the completion provider when it supports embeddings.

API keys are encrypted before being stored in `user_llm_settings`. Read endpoints return provider and model information plus masked keys, never the stored secret. The settings screen can test completion and embedding configurations before they are used by a pipeline.

### 3. Building the Skill Bank

Users can create, update, list, and delete Skill Bank items and their bullet points. Supported item types are:

- `experience`
- `project`
- `skill`
- `education`
- `certification`

Creating or changing an item queues a new item embedding. Updating an item also refreshes its bullet embeddings because their searchable metadata includes the parent item type. Creating or changing a bullet queues its dense and sparse embeddings.

Deleting an item or bullet removes its vectors from both Pinecone indexes before deleting the PostgreSQL data. This prevents stale search results from referring to evidence that no longer exists.

### 4. Importing an existing resume

The resume import accepts PDF and DOCX files up to 10 MB.

1. The API stores the file in the private Supabase `resume-imports` bucket.
2. It creates `resume_imports` and `background_jobs` rows and enqueues the parser.
3. The worker extracts text and asks the user's completion model for structured items and skills.
4. The response must satisfy the Pydantic schema. Server-side checks reject bullets or skills that are not present in the extracted source text.
5. Parsed data remains staged in `resume_imports.parsed_json`; it is not immediately added to the Skill Bank.
6. The user edits, removes, and selects the extracted content.
7. The commit endpoint writes only that final selection and prevents a second commit.
8. Embedding jobs are queued for the imported items and bullets.

### 5. Parsing a job description

The user can paste job-description text or upload a PDF up to 10 MB. Uploaded PDFs are stored privately in Supabase before processing.

The parsing worker extracts and validates:

- required skills
- nice-to-have skills
- responsibilities
- seniority
- ATS keywords
- action verbs
- named technologies and whether a requirement expects `any` or `all` of them

Input sent to the model is capped at 15,000 characters. Model output must match the strict `JDParsed` schema. If the first response is invalid, the worker makes one correction attempt. Named technologies and action verbs are checked against the original job-description text so invented terms are not persisted.

Validated output is stored in `job_descriptions`, `jd_requirements`, and `jd_action_verbs`.

### 6. Matching and selection

After parsing is complete, the frontend calls the matching endpoint. The backend runs the hybrid retrieval and reranking process described above and returns matches grouped by Skill Bank item and job requirement.

The response also identifies requirements with no evidence and indicates whether any Skill Bank records are still waiting for both vectors. The user chooses which real bullet points should continue to rewriting.

### 7. Rewriting and approval

Selecting bullets creates a draft `resume_versions` row tied to the parsed job description. Starting a rewrite moves it to `rewriting` and queues a worker.

The worker supplies the selected originals together with required skills, ATS keywords, action verbs, known technologies, and the user's tags. Proposed text passes through server-side checks for:

- changed, added, or removed numbers and metrics
- technologies not supported by the source evidence
- unsupported factual claims
- rewrites that make too little meaningful change

The result is stored in `resume_bullet_selections`; the source `bullet_points` rows remain unchanged. The review interface shows original and proposed text. A user can edit a proposal, approve it, or explicitly revert to the original. Finalization is rejected until every selection is resolved.

### 8. LaTeX assembly, editing, and compilation

After finalization, an assembly worker groups resolved bullets by their original Skill Bank items and renders the repository's LaTeX template. Approved text is used for approved selections; original text is used for reverted selections. Values are escaped before being inserted into LaTeX.

The generated source is saved on the resume version and can be edited in the frontend. Compilation runs Tectonic with a hard timeout. A successful PDF is stored in the user's private Supabase resume path and accessed through a signed download URL. Compilation failures store a safe diagnostic, including a line number when available.

Users can name resumes, label versions, create snapshots, and navigate the parent-version chain. A snapshot copies the current LaTeX source and PDF reference into a new version without changing the earlier version.

## Why background workers are used

These operations could technically execute inside FastAPI request handlers, but doing so would keep HTTP connections open while waiting on LLM providers, Pinecone, file extraction, Tectonic, or Supabase Storage. Their latency is variable and some can take minutes or hit provider timeouts and rate limits.

ARQ workers are used for:

- PDF and DOCX resume parsing
- PDF job-description parsing
- dense and sparse embedding generation
- bullet rewriting and its safety checks
- LaTeX assembly
- Tectonic compilation and PDF upload

The API validates the request, records the intended operation, enqueues a job, and returns a `202` response with resource and background-job IDs. The frontend polls `/api/background_jobs/{job_id}` and shows the persisted `queued`, `running`, `done`, or `failed` state.

This separation provides practical benefits:

- API requests remain short and do not consume web-server capacity while an external provider is working.
- The result and safe error message survive a browser refresh or disconnected client.
- Worker and API processes can be deployed and scaled independently.
- Tectonic and document extraction do not compete with normal API traffic.
- Each operation has an explicit state transition, ownership check, and timeout.

Fast operations still run in the API. CRUD, reads, review decisions, version metadata, and the current matching endpoint are synchronous. Workers are therefore used selectively, not as a requirement for every action.

## Architecture

```text
Browser (Next.js)
  │
  ├── Supabase Auth ── bearer token
  │
  ▼
FastAPI
  ├── PostgreSQL ── users, evidence, JDs, jobs, resume versions
  ├── Supabase Storage ── uploaded documents and generated PDFs
  ├── Pinecone ── per-user dense and sparse vector namespaces
  ├── LiteLLM ── user-configured completion and embedding providers
  ├── OpenRouter ── candidate reranking
  └── Redis/ARQ ── queued work
                      │
                      ▼
                   ARQ worker
                      └── parsing, embeddings, rewriting, assembly, Tectonic
```

The API and worker use the same services and PostgreSQL database. Redis transports job requests; `background_jobs` is the application-visible record of progress and errors.

## Active data model

```text
users
  ├── skill_bank_items
  │     └── bullet_points
  ├── user_llm_settings
  ├── job_descriptions
  │     ├── jd_requirements
  │     ├── jd_action_verbs
  │     └── resume_versions
  │           ├── resume_bullet_selections ── bullet_points
  │           └── parent_version_id ── resume_versions
  ├── resume_imports
  └── background_jobs
```

### Main tables

| Table | Purpose |
|---|---|
| `users` | Local identity keyed by the Supabase Auth user UUID. |
| `skill_bank_items` | Experiences, projects, skills, education, and certifications with dates, tags, source text, and origin. |
| `bullet_points` | Ordered evidence attached to a Skill Bank item, including tags and optional metrics. |
| `user_llm_settings` | Completion and optional embedding configuration with encrypted API keys. |
| `job_descriptions` | Original text or private file path, validated parsed JSON, and parsing status. |
| `jd_requirements` | Required or preferred requirements plus named technologies and `any`/`all` matching semantics. |
| `jd_action_verbs` | Validated action verbs extracted from a job description. |
| `resume_imports` | Staged PDF/DOCX extraction and the time at which the reviewed data was committed. |
| `background_jobs` | User-owned operation type, status, structured result, and safe error message. |
| `resume_versions` | Resume state, name, label, job description, LaTeX source, PDF path, and optional parent version. |
| `resume_bullet_selections` | Original/proposed text, approval state, guardrail flags, and ordering for one resume version. |

PostgreSQL owns all application content. Pinecone stores searchable representations keyed by the same item or bullet UUID and can be regenerated from PostgreSQL.

## API surface

All `/api` routes require a Supabase bearer token except the supported-model discovery endpoints. The primary route groups are:

| Prefix | Responsibility |
|---|---|
| `/api/skill_bank` | Skill Bank item and bullet CRUD. |
| `/api/settings/llm` | Save, inspect, test, or remove encrypted BYOK configuration. |
| `/api/jd` | Submit, list, and read job descriptions. |
| `/api/match` | Run hybrid matching for a completed job description. |
| `/api/resume_imports` | Upload, inspect, and commit staged resume imports. |
| `/api/resume_versions` | Create, rewrite, finalize, assemble, compile, edit, name, copy, and inspect resumes. |
| `/api/resume_bullet_selections` | Approve, edit, or revert proposed bullets. |
| `/api/background_jobs` | Read persisted asynchronous job state. |
| `/api/storage` | Create user-scoped signed upload and download URLs. |

FastAPI generates the exact current request and response documentation at `/docs` and `/redoc`. Additional endpoint and pipeline details live in [`docs/api`](docs/api).

## Deployment notes

The Next.js frontend is deployed on Vercel, while the FastAPI backend and ARQ worker run on AWS Lightsail. The frontend sends authenticated API requests to the Lightsail backend using the user's Supabase access token.

The Lightsail deployment runs two backend processes from the same codebase:

- The FastAPI process handles authentication, validation, database operations, synchronous matching, and job submission.
- The ARQ worker receives queued work through Redis and performs job-description parsing, resume imports, embedding generation, bullet rewriting, LaTeX assembly, and PDF compilation. Tectonic is required only by this worker process.

Both processes use the same environment configuration and require access to PostgreSQL, Redis, Supabase, Pinecone, OpenRouter, and the configured AI providers. Generated PDFs and uploaded documents are stored in Supabase Storage rather than on the Lightsail instance.
