# CV-Forge
 
**AI-powered, JD-aware resume tailoring platform with a live LaTeX editor.**
 
CV-Forge lets a user build one structured "Skill Bank" of everything they've ever done — internships, projects, skills, GitHub repos, LeetCode activity — and then, for any job description, automatically select and rewrite only the most relevant subset into a tailored, ATS-friendly, LaTeX-typeset resume. No more maintaining five different resume files or manually re-editing bullet points for every application.

## Problem Statement
 
Every job description asks for a different slice of a candidate's experience. A single static resume is rarely optimized for any specific role, and manually rewriting a resume for every application is repetitive and error-prone. Candidates end up either:
 
- submitting one generic resume to every job (weak keyword match, poor ATS pass-through), or
- maintaining many hand-edited resume variants (unsustainable at scale).
CV-Forge solves this by decoupling **content** (a structured, versioned bank of everything the user has done) from **presentation** (a specific resume assembled and typeset for a specific JD).
 
---
 
## Core Concept
 
Instead of storing "a resume," the platform stores **atomic units of truth**:
 
- Every experience/project bullet point is its own record, individually tagged with the skills/technologies it demonstrates.
- Every skill has a source: self-reported, inferred from GitHub activity, or inferred from LeetCode topic strength.
- A job description is parsed into structured requirements (required skills, nice-to-have skills, responsibilities, ATS keywords).
- A resume is generated by **retrieving and ranking** the bullet points most relevant to that specific JD, rewriting their phrasing to mirror the JD's language (without inventing new facts), and rendering them into a LaTeX template the user can further edit by hand.
This granularity is what allows "pull only the 4 most relevant bullets out of 12" instead of all-or-nothing resume blocks.

## Features
 
- **Skill Bank** — structured CRUD for experiences, internships, projects, skills, education, and certifications.
- **JD Parser** — paste text or upload a PDF; extracts required skills, nice-to-have skills, responsibilities, and ATS keywords into structured JSON.
- **Smart Matching** — hybrid semantic (embeddings) + keyword scoring to rank skill bank items against a given JD.
- **Tailored Rewriting** — LLM-assisted rephrasing of selected bullets to mirror JD language, with a mandatory diff/approval step before anything is auto-applied.
- **GitHub Integration** — scans repositories, summarizes what each one demonstrates, and surfaces inferred (not claimed) skills.
- **LeetCode Integration** — pulls topic/difficulty-level solve stats to surface technical strength signals.
- **ATS Compatibility Check** — reports what percentage of a JD's keywords appear in the final generated resume, and flags gaps.
- **In-Browser LaTeX Editor** — live-editable LaTeX source with recompilation, inline error annotations, and PDF preview.
- **Version History** — every generated/edited resume is versioned and can be rolled back.
- **Multi-Resume Management** — generate and store a distinct tailored resume per job application.

└──────────────┘      └─────────┬─────────┘      │    resume versions)    │
                                 │                └─────────────────────┘
                                 ▼
                     ┌────────────────────────┐
                     │   Async Task Workers    │
                     │ (Celery / arq + Redis)  │
                     │                         │
                     │  - JD parsing (LLM)     │
                     │  - Embedding generation │
                     │  - Matching & ranking   │
                     │  - Rewriting (LLM)      │
                     │  - GitHub sync          │

## AI Pipelines
 
### Pipeline A — JD Parsing
Input: pasted JD text or uploaded PDF. Output: structured JSON —
```json
{
  "required_skills": ["..."],
  "nice_to_have_skills": ["..."],
  "responsibilities": ["..."],
  "seniority": "mid",
  "ats_keywords": ["..."]
}
```
Single LLM call constrained to a strict JSON schema.
 
### Pipeline B — Skill Bank Embedding
Every bullet point and skill entry is embedded on create/update and stored in `pgvector`. This is the retrieval index used by the matcher.
 
### Pipeline C — Matching & Ranking
For each JD requirement, compute a hybrid relevance score per skill bank item:
- semantic similarity (cosine similarity between requirement and bullet embeddings)
- keyword/fuzzy overlap (important for literal ATS keyword matching)
- recency weighting (recent experience weighted slightly higher)
Top-N bullets per section are selected within a configurable length budget.
 
### Pipeline D — Tailored Rewriting
Rephrases the *selected, real* bullet points to mirror JD terminology — **rephrasing only, never inventing new facts, metrics, or technologies**. Output is always shown as a before/after diff requiring explicit user approval before being written into a resume version.
 
### Pipeline E — GitHub Scan
Pulls repos via the GitHub API (README, primary languages, commit activity). An LLM summarizes what each repo demonstrates and tags inferred skills with `source: github`, kept distinct from self-reported skills.
 
### Pipeline F — LeetCode Scan
Pulls solved-problem stats by topic/difficulty via the LeetCode GraphQL endpoint, converted into topic-strength signals (e.g., "strong in DP, weak in graphs").
 
### Pipeline G — ATS Compatibility Check
After resume assembly, computes what percentage of the JD's `ats_keywords` appear in the final resume text, and surfaces missing keywords to the user.

## Getting Started
 
### Prerequisites
 
- Python 3.11+
- PostgreSQL 15+ with `pgvector` extension enabled
- Redis 7+
- Tectonic (LaTeX engine) — installed in the worker environment
- Docker & Docker Compose (recommended for local dev)
### Local Setup
 
```bash
# Clone the repository
git clone https://github.com/<your-org>/resumeforge.git
cd CV-Forge
 
# Copy environment template and fill in secrets
cp .env.example .env
 
# Start Postgres, Redis, backend, and worker via Docker Compose
docker compose up --build
 
# Run database migrations
docker compose exec backend alembic upgrade head
```
 
The API will be available at `http://localhost:8000`, with interactive docs at `http://localhost:8000/docs`.
 
### Running Without Docker

```bash
# Enter the backend project after cloning the repository
cd server

# Create .env from the tracked template, then fill in its values
cp .env.example .env

# Create server/.venv and install the exact locked dependencies
uv sync

# Apply database migrations
uv run alembic upgrade head

# Start the API with uvicorn app.main:app --reload
uv run app
```

The API is available at `http://localhost:8000`. On another machine, install
[uv](https://docs.astral.sh/uv/getting-started/installation/), clone the repository, and run the
same commands. `uv sync` creates the virtual environment automatically when it does not exist.

For pip-based environments, install the locked runtime dependencies exported from the same uv
lockfile:

```bash
cd server
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

## LaTeX Compilation
 
- Compilation runs via **Tectonic**, a self-contained TeX engine (no full TeXLive install required).
- Each compile request runs in a **sandboxed subprocess with a strict timeout** to prevent runaway or malicious LaTeX from affecting the host.
- Compilation errors are parsed from Tectonic's output and returned as structured, line-annotated errors rather than a raw log dump, so the frontend editor can highlight the offending line.
- Every save creates a new version row (`resume_versions`), enabling rollback.

## Third-Party Integrations
 
### GitHub
- OAuth2 flow to connect a user's account.
- Pulls repository metadata, README content, primary languages, and commit activity via the GitHub REST API.
- Skills inferred from repos are tagged `source: github` and kept visibly distinct from self-reported skills.
### LeetCode
- No official public API exists; integration uses the commonly-used unofficial LeetCode GraphQL endpoint.
- Because this is an unofficial interface, it may change without notice — sync jobs are built to fail gracefully and surface a "sync unavailable" state rather than erroring the whole pipeline.

## Guardrails Against AI Hallucination
 
Because this tool generates content that represents a user's real professional history, the rewriting pipeline is deliberately constrained:
 
1. Rewriting prompts explicitly forbid introducing new technologies, metrics, or claims not present in the source bullet.
2. Every LLM-rewritten bullet is diffed against the original; any new noun/skill/number not present in the source or the user's tagged skills is flagged for review.
3. Nothing is auto-applied to a resume version — the user must explicitly approve each rewritten bullet.
4. GitHub- and LeetCode-inferred skills are stored with a `source` field and never silently merged into self-reported skills.

## Deployment
 
- Containerized via Docker; recommended orchestration via Docker Compose (small scale) or Kubernetes (production scale).
- Background workers should be scaled independently from the API layer, since LLM calls and LaTeX compilation are the primary latency/cost drivers.
- Recommended: separate worker pools for "fast" jobs (JD parsing, matching) vs. "heavy" jobs (LaTeX compilation, GitHub sync) so a slow compile doesn't block JD parsing throughput.
